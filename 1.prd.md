PRD — VerifiCode
Verifiable Proof-of-Work Engineering Discovery & Hiring Platform

Problem Statement: HM26-P2-02
Track: HR Tech · Developer Platforms & Talent Verification
Core idea: Build → Prove → Defend → Verify → Compete → Discover → Hire

1. Product Overview
Product Name

VerifiCode

One-line pitch

A proof-of-work engineering platform where developers prove what they can build, explain, and solve — while recruiters discover candidates through verified engineering evidence instead of resumes alone.

Core problem

Traditional hiring relies heavily on:

resumes
degrees
CGPA
self-reported skills
certificates
interviews

These provide limited evidence of whether someone can actually:

build software
solve engineering problems
explain their architecture
debug systems
make technical decisions
understand their own code

VerifiCode creates a continuous evidence loop:

CHALLENGE
    ↓
BUILD
    ↓
DOCUMENT
    ↓
VERIFY
    ↓
DEFEND
    ↓
REVIEW
    ↓
CAPABILITY SIGNALS
    ↓
RECRUITER DISCOVERY
    ↓
OUTREACH
2. Product Vision

The platform should move hiring from:

"I claim I know this."

to:

"Here is the work I built.
Here is how I built it.
Here is why I made these decisions.
Here is evidence that I understand it.
Here is independent review of the work."

4.4 ADR System

ADR = Architecture Decision Record

Example:

ADR-001

Decision: Use Redis for rate limiting.

Problem: API must prevent excessive requests.

Options:

PostgreSQL
Redis
In-memory cache

Chosen: Redis

Reason:

Fast temporary key-value operations make Redis suitable for request counters.

Trade-off:

Introduces an additional infrastructure dependency.

This gives recruiters evidence of engineering reasoning, not merely technology names.

Important:

The platform should avoid claiming that one signal proves that a candidate wrote everything themselves.

9. Important Anti-Gaming Principle

Do not implement:

Large paste = CHEATING

or:

AI-like code = CHEATING

Those signals are insufficient by themselves.

Instead:

Multiple signals
      ↓
Integrity Engine
      ↓
Evidence Report
      ↓
Risk/Suspicion Level
      ↓
Human Review when necessary

Example:

INTEGRITY REPORT

Paste Activity          HIGH
Tab Switching            LOW
Code Evolution           NORMAL
Repository Similarity    LOW
Typing Pattern           NORMAL

Status:
REVIEW REQUIRED

Possible statuses:

VERIFIED
NORMAL
REVIEW REQUIRED
DISQUALIFIED

A disqualification should require defined rules/evidence rather than an opaque AI judgment.

15. Question Scoring

Use multiple dimensions instead of only one number:

Technical Correctness
Project Consistency
Completeness
Clarity
Reasoning

Example:

REST API              88
Database              92
Authentication        75
Architecture          85
Error Handling        80

Project Understanding
                     84/100

The score should be presented as an assessment signal, not as an absolute measurement of a person's ability.

16. Adaptive Questioning

The AI can change the next question based on previous answers.

Example:

Q1:
Explain your authentication system.

Candidate gives weak answer.

        ↓

AI detects uncertainty around JWT.

        ↓

Q2:
Where is the JWT generated and
how is it validated in your code?

        ↓

Candidate answers.

        ↓

Q3:
What happens if the token expires?

This makes the defense more meaningful than asking five random questions.

Must include:

Authentication
JWT/session-based authentication
secure password hashing
OAuth where applicable
role-based access control
Candidate data
encrypted sensitive data
private repository tokens never exposed to frontend
least-privilege GitHub permissions

sandboxed code execution

container isolation

44. Privacy

Because the system records coding-session telemetry and potentially voice/video:

This assessment may collect:

✓ Screen-sharing status
✓ Challenge activity
✓ Editor events
✓ Test execution
✓ Optional camera/microphone
✓ Voice responses

Candidate must explicitly consent.

Do not secretly record users.
